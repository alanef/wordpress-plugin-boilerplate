# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Release hooks for `/tk-release`, rendered into every plugin as `scripts/release/`: `bump-version.sh X.Y.Z` sets the header, version constant, Stable tag, package.json, `.pot` and changelog heading, then reads every one back and fails on any mismatch, because a substitution that matches nothing fails silently (`--check` reads back only); `check-dependencies.sh` resolves the shipped Composer dependencies fresh and blocks on any advisory, warning only for tooling and npm trees; `run-tests-and-mark.sh` runs checks.yml's gates locally and writes `TESTS_PASSED.md`, naming the commit, only when all pass. Generalised from Quick PayPal Payments, so every plugin releases the same way instead of by hand.
- `/tk-deploy live` commands, rendered as `.claude/commands/deploy-live.md` from one template per pipeline: GitHub-only, single-tag (`Type: free`/`freemium`/`premium`), the two-tag Freemius pipeline (`"pipeline": "freemius-two-tag"`) and own-site plugins (`"pipeline": "own-site"`, which builds and hands off to HOSTING DevOps rather than deploying). All share one set of preconditions (level with origin, clean tree, versions agree, tag absent, fresh test evidence, CI green), require explicit confirmation before tagging, never retry a tag push, and finish with the KB changelog and YouTrack.
- Release-only sync for plugins on their own pipeline: with `"pipeline": "freemius-two-tag"` or `"own-site"`, or `--release-only`, the sync applies only the changelog migration, `bump-version.sh`, `check-dependencies.sh` and `deploy-live.md`, and logs what it skipped. A full sync would have overwritten Quick PayPal Payments' Freemius release.yml, its two-suite test setup and its composer scripts. A project's own unmanaged `run-tests-and-mark.sh` is kept.
- The deploy commands' YouTrack step matches Quick PayPal Payments': Resolution `Done` when unresolved, Fix versions `$V` only when that version already exists (never created), and an issue whose commits in range touch only paths outside the plugin directory gets the release comment but keeps its Stage, decided by the paths changed rather than the commit subject.
- The deploy commands no longer skip the KB changelog quietly when `.env.wordpress` is missing. That file is gitignored, so a re-clone or move loses it (Quick PayPal Payments' did, during its 6.0.5 release), and a quiet skip ships a stale public changelog. A plugin has a KB page if `changelog_url` is pinned or its readme links one. Then the preconditions stop before tagging unless `.env.wordpress` sets `WP_POST_ID` and `CHANGELOG_FILE`, or the user explicitly accepts a stale page. A skipped or failed publish, or a page not showing the new version, puts its own `CHANGELOG PAGE NOT UPDATED` line in the final report. Only plugins without a KB page skip, with the note "no KB changelog page".
- The sync refuses a Freemius plugin (any `fs_dynamic_init(` in the plugin directory) whose `.tooling.json` pins no `pipeline`. A full sync would overwrite the workflows of a plugin on its own Freemius pipeline, and nothing in readme.txt tells the pipelines apart.
- `free_tag_prefix` pin for the two-tag Freemius pipeline, because a free repo can tag differently from its dev repo. Display Eventbrite Events tags `v6.7.2` in the dev repo and `6.7.2` in the free repo, and the deploy command would have pushed `v6.7.3` to the free repo. It defaults to `tag_prefix`, so Quick PayPal Payments is unchanged.
- `"freemius_deploy": "workflow"` pin for a single-tag Freemius plugin (`Type: premium` or `freemium`) whose own release.yml uploads the build to Freemius as beta. Its `/tk-deploy live` then checks that upload and says to promote the beta to released, instead of saying no Freemius deploy step exists and telling the user to upload the zip by hand, which would have uploaded it twice. Needs `freemius_id`. First used by Rightmove to XML.
- New `.tooling.json` pins: `tag_prefix` (otherwise taken from the newest existing tag), `youtrack_project`, `pipeline`, `free_repo`, `freemius_id`, `changelog_url`, `hosting`.
- Freemius free build check, rendered as `scripts/freemius/` into every Freemius plugin with a free version (`"pipeline": "freemius-two-tag"` or `Type: freemium`). Freemius makes the wordpress.org build by stripping premium code, and a missed guard either ships paid code to wordpress.org or leaves a call to stripped code that fatals. So the free zip Freemius actually generates is checked: an alpha is uploaded to Freemius as pending (offered to nobody until released) and its free zip downloaded (`freemius-free-build.js`), then statically scanned (`check-free-build.sh`, `free-build-scan.php`: leaked premium definitions, guards the stripper missed, calls to stripped code, `@fs_premium_only` paths, a project denylist) and run alone on a clean WordPress (`smoke-free-build.sh`). The same checks go in each plugin's release.yml before the free build is pushed. Run against the live builds, they found premium code and calls to stripped code in Display Eventbrite Events 6.8.0, and a premium branch and a premium-only class in Anti-Spam 3.1.0. Runs from a `free-check/<version>` branch push, because GitHub offers "Run workflow" only for workflows on the default branch, which is the release branch in two-tag repos. The runtime check sweeps the admin menu before and after skipping the Freemius opt-in, since Freemius hides some menus until then (QPP's main screen).
- The free build runtime check also loads every page it visits, and the block editor, in a headless browser (`smoke-browser.js`, Playwright). It fails on an uncaught error from the plugin's scripts, a plugin asset that does not load, or a block whose `block.json` ships but is not registered in the editor. Display Eventbrite Events 6.9.0-beta.4 passed the PHP-only check with its block missing from the inserter: `index.js` threw because its variables were localized on a script handle only the premium build registers. The browser check fails beta.4 and passes the fixed beta.5.

### Changed

- Each plugin now has exactly one changelog, `<plugin-dir>/changelog.txt` in wp.org style with typed bullets under `= Unreleased =`. It ships in the zip and is what the KB publisher reads. The sync no longer creates a root `CHANGELOG.md`: it creates `changelog.txt` if missing (from the readme's changelog entries, or a baseline), merges any real entries from an existing root `CHANGELOG.md` into it, and deletes that file. Two changelogs had started to diverge, and the root one never reached users.
- `check-dependencies.sh` audits a committed plugin `composer.lock` as it stands, but sets an untracked local one aside and resolves fresh as CI does, then restores it. A stale local lock (Quick PayPal Payments keeps one, gitignored) was being audited instead of what the release actually ships.
- The changelog migration no longer duplicates a release: a version already in `changelog.txt` keeps its wording, and `CHANGELOG.md` entries only fill new versions, Unreleased and `* Baseline.` stubs. Stop User Enumeration 1.7.9 and Contact Form Clean and Simple 4.12.3 were each told twice in the first rollout pass.
- A readme.txt link to the GitHub `CHANGELOG.md` is repointed at `<plugin-dir>/changelog.txt`, since the sync deletes the file it linked.
- A GitHub-only plugin with no `Requires PHP:` header is refused before the sync writes anything. It used to fail halfway, leaving rewritten workflows and an updater class behind (umami-tracking).
- The GitHub release body links to `<plugin-dir>/changelog.txt` instead of the root `CHANGELOG.md`.
- `bump-version.sh` also sets the version in the `package-lock.json` beside each versioned `package.json`, at the top level and in `packages[""]`, and reads both back. npm keeps the version there twice, and after `/tk-release` the lock was left on the old version (Display Eventbrite Events).

### Fixed

- `check-dependencies.sh` no longer blocks a release when the plugin's `composer.json` only autoloads. The fresh resolve gives a lock with no packages, and `composer audit` exits 1 on that ("No installed packages found"), which the script read as advisories in shipped code. It now reports "none shipped" (Fullworks Gravity Image Resize).
- The synced `.gitignore` now ignores `.wp-env/`. Docker creates it as a root-owned folder (an `mu-plugins` stub) when wp-env maps one, so it showed as an untracked change in plugin repos (Anti-Spam), and a root-owned folder can't be removed without sudo. The boilerplate's own `.gitignore` already had it, but the synced copy didn't.

## [1.1.0] - 2026-10-09

### Added

- GitHub-only plugins (no `Type:` in readme.txt) now update themselves from their GitHub releases through the normal WordPress update screens, so sites no longer need manual zip uploads or a Git Updater plugin (which cannot work here: it expects assets named after the repository, not the plugin folder). The sync renders a per-plugin `includes/class-github-updater.php`, sets the `Update URI` header from the git remote, adds a guarded `require` to the main file and excludes Plugin Check's `plugin_updater` check; adding a `Type:` removes all of it, because WordPress.org forbids off-site updates. It reads the latest release from the github.com redirect (no API, token or rate limit), caches it (6 h, 1 h after a failure, 5 s timeout) so an unreachable GitHub never slows the admin, keeps an update in the folder the plugin is installed in, and ships with a generated PHPUnit test. A synced copy was chosen over a Composer library because a shared class loaded by several plugins resolves to whichever loads first.
- `Build Release` now reads a `Type:` header from the plugin's `readme.txt` to decide where a release goes, so the same workflow serves every repo and a GitHub-only plugin no longer needs a hand-edited, divergent `release.yml`. No header means GitHub only, `free` adds WordPress.org, `freemium` adds WordPress.org and Freemius, `premium` is GitHub and Freemius. WordPress.org accepts non-standard readme headers, so the tag ships harmlessly. An unrecognised value fails the release rather than falling back to the default: a typo that silently skips WordPress.org is only noticed when someone asks why an update never landed. Resolved targets are printed in the job log and the run summary.
- `run-tests.sh` now runs a plugin's pure unit suite on the host, with no WordPress loaded, when `tests/phpunit-unit.xml.dist` exists. Such a suite stubs `wp_remote_post()` and friends behind `function_exists()`; run under the wp-env bootstrap the real WordPress functions already exist, so the stubs never install and the tests issue live HTTP. They then fail as though the product were broken. Pair it with `"phpunit_exclude": ["unit"]` in `.tooling.json` so the wp-env suite does not run them a second time.
- `wp-env start` in the PHPUnit job now retries up to three times, stopping between attempts so a half-started environment does not poison the next try, and fails loudly with an annotation if all three fail. It flakes intermittently on container and network timing, and a flake previously read as a test failure. The fix existed in the boilerplate's own CI but had never reached the template, so no plugin had it.
- Plugin Check now runs on `develop` as well as the repository's default branch. Work lands on `develop`, so a check wired only to the default branch reported nothing until merge time, which is exactly when it is least useful. The generated workflow takes a `__BRANCH_LIST__` block instead of a single `__BRANCH__`, deduped so a repo whose default already is `develop` gets one entry rather than two.

### Fixed

- `bin/setup-plugin.sh` no longer turns the main file's `Plugin Name:` header into `<name>: <name>`. Its placeholder replacement also matched the header key, so every new plugin started with a broken header and the tooling sync it runs could not find the plugin ("Could not determine plugin directory").
- The Plugin Check and Build Release jobs no longer fail with `wp: command not found` when setup-php intermittently reports "Could not setup wp-cli" (it carries on regardless, so the job only died later at the dist-archive step). A new `Ensure WP-CLI` step downloads the phar directly, with retries, whenever setup-php did not provide it. It failed 3 of 7 runs while releasing fullworks-gravity-to-listmonk 1.0.0, each needing a manual re-run.
- Plugin Check now lists the built zip's contents and deletes any `.wp-env.override.json` before starting wp-env. A committed override with a `plugins` entry mounts the source directory over the build mapping, so Plugin Check inspected the repository (reporting `.distignore` as a hidden file) instead of the zip.
- `bin/sync-tooling.sh` no longer resets a plugin repo's `package.json` version or downgrades a dev dependency the repo has already moved past (e.g. `@wordpress/env` 11).
